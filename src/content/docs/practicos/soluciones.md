## Normalización y SQL

### B3-BBDD-01
[Volver al ejercicio](/AstroXmind/practicos/cuaderno/#b3-bbdd-01)

**Respuesta Correcta**: **Sí, pues cada campo contiene un valor atómico dentro del dominio definido.**

**Justificación Técnica**: 
En el modelo relacional, un atributo es atómico si no contiene listas, conjuntos repetitivos o subtablas anidadas. A nivel de diseño, guardar `nombre y apellidos` en un campo de texto no viola formalmente 1FN salvo que el modelo exija explícitamente la descomposición por requisitos de negocio.

### B3-BBDD-02
[Volver al ejercicio](/AstroXmind/practicos/cuaderno/#b3-bbdd-02)

**Respuesta Correcta**: **No, existen dependencias funcionales parciales.**

**Justificación Técnica**: 
Se supone además que `(dni, curso, modulo)` es clave candidata y que no existen dependencias adicionales que la hagan no mínima. La clave primaria es `(dni, curso, modulo)`. Los atributos `nombre`, `apellidos` y `direccion` dependen únicamente de una parte de la clave (`dni`), es decir: `dni -> {nombre, apellidos, direccion}`. Para cumplir 2FN, todo atributo no principal debe tener **dependencia funcional completa** de toda la clave.

### B3-BBDD-03
[Volver al ejercicio](/AstroXmind/practicos/cuaderno/#b3-bbdd-03)

**Respuesta Correcta**: **3FN y BCNF bajo las dependencias funcionales indicadas a continuación**. No basta observar nombres de columnas: se supone que `dni` determina los datos del usuario, `idcurso` determina los datos del curso y `(dni, idcurso)` determina la nota; no hay otras dependencias no triviales ni claves alternativas que cambien el análisis.

**Justificación Técnica**:
- Cada tabla representa una única entidad o relación.
- No existen atributos multivaluados (1FN).
- No existen dependencias parciales (2FN).
- No existen dependencias transitivas entre atributos no clave (`X  → Y  → Z`) (3FN).

### B3-BBDD-04
[Volver al ejercicio](/AstroXmind/practicos/cuaderno/#b3-bbdd-04)

**Respuesta Correcta**: Con las claves habituales (`idCliente`, `idVendedor`, `idVenta`, `idArticulo` y `(idVenta,idArticulo)`) y sin otras dependencias no triviales, el esquema cumple BCNF. La ausencia de dependencias multivaluadas independientes debe declararse como hipótesis; no puede deducirse solo del listado de columnas. Bajo esa hipótesis no se requiere otra descomposición para 4FN.

| Iteración | i al comenzar | a después de sumar | Salida | Siguiente i |
|---|---:|---:|---|---:|
| 1 | 1 | 6 | `1,6 ` | 3 |
| 2 | 3 | 9 | `3,9 ` | 5 |

#### Estructura de Unidades Organizativas (OUs):
| Ruta organizativa | Contenido |
|---|---|
| organismo.age.es / OU_Organismo / OU_Servidores | Servidores |
| organismo.age.es / OU_Organismo / OU_Direccion | Dirección |

| organismo.age.es / OU_Organismo / OU_Administracion / Equipos | Puestos administrativos |

Las directivas de equipo deben alcanzar la OU de los equipos; las de usuario, la OU de los usuarios. Una única vinculación sin comprobar el ámbito no garantiza ambas.

#### Configuración de la GPO `GPO_Seguridad_Puestos`:
1. **Bloqueo de USBs**:
   - Ruta: `Configuración del equipo` `→` `Directivas` `→` `Plantillas administrativas` `→` `Sistema` `→` `Acceso de almacenamiento extraíble`.
   - Directiva: **"Todas las clases de almacenamiento extraíble: denegar todo acceso"** `→` `Habilitada`.
2. **Bloqueo por Inactividad (10 minutos = 600 segundos)**:
   - Ruta: `Configuración de usuario` `→` `Plantillas administrativas` `→` `Panel de control` `→` `Personalización`.
   - Directivas:
     - *"Habilitar protector de pantalla"*: `Habilitada`.
     - *"Proteger el protector de pantalla mediante contraseña"*: `Habilitada`.
     - *"Tiempo de espera del protector de pantalla"*: **`600`** segundos.

## DMZ y filtrado

### B4-SEGURIDAD-01

Para publicar `203.0.113.1:80/443` hacia `192.168.10.50` falta DNAT en PREROUTING, además de reenvío IP y rutas de retorno. Las reglas de filtrado siguientes no bastan por sí solas para esa publicación.
[Volver al ejercicio](/AstroXmind/practicos/cuaderno/#b4-seguridad-01)

```bash
# Ejemplo de laboratorio: no ejecutar en sistemas en uso.
# Faltan DNAT, reenvío IP, rutas y reglas operativas DNS/NTP.
#!/bin/bash
# 1. Limpieza de reglas previas
iptables -F
iptables -X
iptables -t nat -F

# 2. Políticas por defecto DROP (Principio de mínimo privilegio)
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT DROP

# 3. Permitir tráfico en interfaz loopback local
iptables -A INPUT -i lo -j ACCEPT
iptables -A OUTPUT -o lo -j ACCEPT

# 4. Permitir paquetes de conexiones ya establecidas y relacionadas
iptables -A FORWARD -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A OUTPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# 5. Permitir tráfico HTTP (80) y HTTPS (443) desde Internet hacia la DMZ
iptables -A FORWARD -i eth0 -o eth1 -p tcp -d 192.168.10.50 -m multiport --dports 80,443 -m state --state NEW -j ACCEPT

# 6. Permitir consulta del Servidor Web DMZ al MySQL en Red Interna
iptables -A FORWARD -i eth1 -o eth2 -p tcp -s 192.168.10.50 -d 192.168.20.100 --dport 3306 -m state --state NEW -j ACCEPT

# 7. Permitir SSH (22) únicamente desde el PC del Administrador (192.168.20.10)
# Al Firewall local:
iptables -A INPUT -i eth2 -p tcp -s 192.168.20.10 --dport 22 -m state --state NEW -j ACCEPT
# Al Servidor Web DMZ:
iptables -A FORWARD -i eth2 -o eth1 -p tcp -s 192.168.20.10 -d 192.168.10.50 --dport 22 -m state --state NEW -j ACCEPT
```
