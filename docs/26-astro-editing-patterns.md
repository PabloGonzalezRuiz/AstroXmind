# Patrones de edición en wikis y sitios Astro alojados en GitHub

Investigación inicial: 18-11-2026; muestra comparativa revisada el 19-11-2026. Complementa la [propuesta de edición](25-wiki-editing-proposal.md) y la [hoja de ruta](03-roadmap.md). Informe de AST-035.

## Resumen ejecutivo

Sí es posible editar documentación desde una web estática de Astro cuyo contenido vive en GitHub. En los repositorios revisados aparecen dos soluciones principales: (1) un enlace que lleva al editor de GitHub, donde GitHub autentica y gestiona commit/fork/PR; (2) un CMS accesible desde el sitio, que requiere un proveedor de autenticación/backend o un servidor propio para escribir en GitHub. Una wiki nativa de GitHub es otro producto, independiente del sitio Astro.

La muestra contiene **11 repositorios públicos**, todos con Astro verificado en `package.json` (dependencia o dependencia de desarrollo); **10** tienen alguna señal documental directa de edición o contribución en el sitio/repositorio. Entre esos 10: **5** configuran enlaces de edición Starlight a GitHub, **1** enlaza el árbol fuente de GitHub, **3** incluyen un panel Decap CMS con un servicio OAuth/gateway, y **1** documenta la contribución a través de otra página wiki. No es un censo ni una muestra aleatoria de todos los repositorios Astro públicos. Es una muestra intencional de documentación Astro/Starlight y ejemplos CMS seleccionados mediante búsquedas públicas de GitHub y revisados en sus manifiestos/configuración; el buscador ordena por relevancia, los repositorios pueden cambiar y los ejemplos CMS no representan la prevalencia general.

La inclusión de una configuración no acredita que el servicio siga activo ni que el proceso funcione actualmente en producción. Se inspeccionaron dos proyectos CodeStitch similares, así que la muestra incluye ejemplos repetidos de una misma familia de starters y no equivale a 11 arquitecturas independientes.

## Patrones y qué enseñan

1. **Enlace a GitHub (5 casos confirmados).** Es la vía con menos piezas propias: la wiki muestra un botón «Editar»; GitHub gestiona login, permisos, editor, fork y PR. No es un editor embebido en Astro, pero la persona empieza desde la página que está leyendo. Starlight resuelve la URL con `editLink.baseUrl`.
2. **Enlace al repositorio (1 caso).** Sigue usando GitHub para autenticación y guardado, pero añade navegación manual al archivo; ofrece una experiencia menos directa.
3. **CMS en el sitio (3 ejemplos actuales + 1 starter legado).** El panel puede estar servido como estático en `/admin`, pero el acceso al repo depende de otro componente: DecapBridge, OAuth proxy en Cloudflare Worker o Netlify Identity/Git Gateway. El contenido suele guardarse en archivos Markdown del repositorio; el modo directo o por PR depende de la configuración/servicio.
4. **GitHub Wiki.** Es adecuada como wiki editable nativa para texto sencillo; su almacenamiento y permisos pertenecen al servicio GitHub Wiki, separado del build y navegación Astro. No proporciona por sí sola edición dentro del árbol AstroXmind.
5. **Editor personalizado.** La muestra no mostró otros editores integrados Astro de uso general con una API de escritura independiente; no debe interpretarse como ausencia de ellos en el universo público.

La guía de [GitHub Wiki](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages) explica que la wiki se edita en GitHub y guarda cambios como commits en su repositorio separado. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site) sirve el sitio estático y no admite lenguajes de servidor; esto no impide que la interfaz estática invoque una API alojada aparte.

## Encaje en AstroXmind y recomendación

AstroXmind ya tiene un editor Markdown con vista previa y borradores locales en la página de prueba (hito `d87deba` según el historial del proyecto). Falta la identidad/autorización y persistencia. Además, el contenido tiene MD/MDX, anotaciones TreeTable, IDs, rutas y metadatos de navegación: un CMS genérico puede editar campos/texto, pero no debe reordenar o renumerar ramas sin conocer las reglas del árbol y las referencias.

**Recomendación por etapas:**

- **Etapa 1, útil ya y de bajo coste:** añadir «Editar en GitHub» a cada documento y configurar Starlight para usar la ruta fuente exacta. Para usuarios con permisos, GitHub abre el editor; para los demás, fork + PR. No requiere guardar tokens ni API propia. Es la opción más rápida si se acepta que la edición final sucede en GitHub.
- **Etapa 2, editor integrado:** conservar el editor AstroXmind existente y conectar un backend pequeño separado (por ejemplo, Cloudflare Worker/Pages Function). El Worker autentica al usuario mediante GitHub App, valida sesión/CSRF/origen, limita repositorio y rutas, valida el documento y el esquema del árbol, y crea una rama de edición y PR. La clave privada de la App permanece como secreto del Worker. Solicitar permisos mínimos de GitHub App: Contents write y Pull requests write; el token de usuario no puede exceder permisos del usuario. Evitar guardar automáticamente en `main`; los cambios estructurales deben revisarse y pasar CI antes de publicar.
- **Etapa 3, si crece la administración editorial:** evaluar DecapBridge/Tina u otro CMS. Configurar widgets/validaciones propios para los metadatos AstroXmind y probar que respete TreeTable y referencias; el coste operativo de un servicio externo y el modelo de permisos dependen del proveedor.

### Costes y riesgos

- **Enlace GitHub:** sin infraestructura adicional de edición; el coste principal es la implementación del enlace y el proceso humano de revisión. Requiere cuenta GitHub para guardar; el editor y los PR son los de GitHub.
- **API propia:** coste inicial mayor (OAuth/App, endpoint, controles de seguridad, pruebas y mantenimiento). Cloudflare publica plan Workers gratuito con límites y plan de pago desde **5 USD/mes**, más cargos por uso excedente según precios vigentes el 13-11-2026; revisar la [tabla actual](https://developers.cloudflare.com/workers/platform/pricing/) antes de elegir. No se estima coste total de AstroXmind sin medir uso ni decidir arquitectura.
- **CMS alojado:** puesta en marcha potencialmente más rápida, pero añade dependencia, configuración de usuarios/roles y posible coste según el proveedor/plan. Decap CMS como interfaz no elimina la necesidad del backend OAuth/Git Gateway.
- **Riesgos comunes del editor integrado:** credencial expuesta en JS público, token demasiado amplio, escritura directa en main, edición concurrente que pisa contenido, rutas/metadatos inválidos, abuso CSRF/XSS y drift entre el preview y la compilación Astro. Mitigaciones: GitHub App con permisos mínimos, secretos en servidor, rama + PR, comprobación de SHA base, validación server-side y build/CI antes de aceptar.

Los permisos granulares de [GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app) permiten limitar acceso a Contents y Pull requests. GitHub confirma que un cliente SPA no puede proteger su client secret; recomienda PKCE, que protege el flujo pero no convierte un secreto desplegado en secreto ([buenas prácticas de GitHub Apps](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app)). Para Pages, mantener el sitio público estático y externalizar el endpoint de guardado es compatible con la restricción documentada.
